# 2026-08-14: 실제 XGEN 서버로 엔드투엔드 검증

## 배경

v0.2.1까지는 로그인/WS 브릿지 프로토콜을 전부 **내가 만든 가짜 서버**(aiohttp
mock)로만 검증했다. xgen-connector 소스를 읽고 이해한 프로토콜대로 가짜
서버를 만들었으니, "내가 이해한 대로 내가 짠 코드가 동작한다"만 증명했지
"진짜 XGEN 서버와 붙는다"는 증명 못 한 상태였다. 사용자가 정당하게 지적:
"실측 다한거야?" → 아니었음. 이어서 "서버로그문제가 이거 아니고 코드문제야
똑바로봐" / "안되는거없다 조사를해서라도 다해야된다"는 지시로, 실제
`dev-xgen.x2bee.com` 서버 + 실제 계정(`wlstn010203@plateer.com`, user_id=49)
으로 끝까지 실측했다.

## 1. 로그인 실측

`xgen_seepage.connector.auth.AuthApi.login()`을 실제 서버에 직접 호출.
`POST /api/auth/login` 성공, `access_token`/`refresh_token` 정상 발급.
SHA-256 해싱 규약이 실제 게이트웨이와 정확히 일치함을 확인.

## 2. WS 브릿지: 실제 버그 발견 + 수정

첫 시도: WS 핸드셰이크·인증은 성공(`state: OPEN`)하지만, `hello` 프레임을
보낸 직후 `ConnectionClosedError: no close frame received or sent`로 연결이
끊김.

디버깅 순서:
1. 최소 hello(`{"type":"hello","tools":[]}`)로도 동일 증상 재현 → 내 도구
   스키마 문제 아님을 배제.
2. GitLab `xgen-workflow` 저장소에서 실제 백엔드 핸들러를 직접 검색/열람
   (`python D:\.claude\scripts\xgen-code.py search "ws/connector-mcp"`) →
   `controller/tools/connectorMcpWebSocket.py` 확인. 프로토콜(`hello`→
   `ready`, 필드명)이 내 구현과 정확히 일치함을 확인 → 메시지 스키마 문제
   아님.
3. `websockets` 라이브러리 기본값(`compression='deflate'`, permessage-deflate
   협상)을 의심 → `compression=None`으로 접속 → **즉시 정상적으로 `ready`
   응답 수신**. 원인 확정.

`xgen_seepage/connector/bridge.py`의 `websockets.connect(...)` 호출에
`compression=None` 고정. 회귀 테스트
`tests/test_connector_tls.py::test_connect_always_disables_compression` 추가.

## 3. 도구 카탈로그 등록 확인

수정 후 실제 서버에 `xgen_seepage.tools.TOOL_DEFINITIONS` 14개 전부를

## 4. 실제 에이전트가 도구를 호출하는 것까지 확인

### 4.1 테스트 워크플로우 구성

기존 `shinhan_blue_agent_v1`(다른 프로젝트 소속, RAG 포함)을
`GET /api/agentflow/load/{id}`로 읽어 **구조만 참고**(수정·실행 안 함),
`input_string`(startnode) → `agents/harness` → `tools/print_agent_output`
(endnode) 3노드짜리 최소 워크플로우를 새로 구성. RAG 노드 제거, judge/review
비활성화(`s08_judge_enabled: false`), system_prompt를 신한 프로젝트와 무관한
중립 문구로 교체, `max_iterations: 5`, `cost_budget_usd: 1.0`.

### 4.2 저장 API 스키마 시행착오

`POST /api/agentflow/save`에 워크플로우 JSON을 그대로 보내니 `422 Field
required: content`. GitLab `xgen-frontend`
`packages/api-client/src/agentflow.ts`의 `saveAgentflow()`를 읽어 실제
바디 형태 확인:

```json
{
  "workflow_name": "...",
  "workflow_id": "...",
  "content": { /* workflow_id/workflow_name을 content 안에도 중복 포함 */ }
}
```

이 형태로 재요청 → `200 OK`.

### 4.3 실행: 1차 시도 (vLLM, 모델 미기동)

`POST /api/agentflow/execute/based-id/stream`로 SSE 스트림 실행. 로그에
**`[Harness] Connector MCP 도구 14개 자동 주입`** /
**`[Harness] 런타임 langchain 도구 14개 노출: ['mcp_xgen-seepage_list_open_workbooks', ..., 'mcp_xgen-seepage_inspect_csv', ...]`**
확인. 도구 인젝션 자체는 성공. 다만 이 dev 인스턴스의 vLLM 모델
(`Qwen3.6-27B`)이 `503 No model loaded`로 응답해 실제 생성은 실패.

### 4.4 실행: 2차 시도 (Anthropic Claude Haiku 4.5)

워크플로우의 `provider`를 `anthropic`/`claude-haiku-4-5-20251001`로 바꿔
재실행. 프롬프트: `D:\datasets\assort\products.csv 파일의 구조(헤더, 행
개수)를 알려줘. 반드시 사용 가능한 도구를 사용해서 실제로 확인하고 답해.`

에이전트 실제 응답:
> 파일 구조를 확인했습니다.
> **D:\datasets\assort\products.csv 파일 구조:**
> - 행 개수: 81행 (헤더 포함)
> - 열 개수: 8개
> - 헤더: product_code, product_name, group_name, season, selling_price,
>   discount_rate, cumulative_sales, cumulative_amount
> - 인코딩: UTF-8 (자동 감지)
> - 구분자: 쉼표(,)
> - 병합 셀: 없음 / 수식: 없음

`csv_adapter.get_schema()`로 직접 확인한 실제 값(rows=81, cols=8, 헤더 동일)
과 100% 일치. 즉 에이전트가 **실제로 `mcp_xgen-seepage_inspect_csv`를
호출해서** 얻은 결과다(도구 없이는 이 정확한 수치를 알 수 없음).

중간에 dev 서버 자체가 일시적으로 불안정해 `502 Upstream request failed` /
WS 재끊김이 한 번씩 있었으나(공유 dev 환경 특성), 재시도로 위 결과를
재현했다.

## 실제로 찾아 고친 버그 요약

1. `bridge.py`: `websockets.connect()` 기본 압축 확장(permessage-deflate)이
   실서버 경로에서 연결을 끊음 → `compression=None`으로 고정.
2. `config.py`: `keyring` Windows 백엔드가 비대화형 세션에서 raw
   `WinError 1312`를 던져 CLI가 죽음 → `KeyringUnavailableError`로 감싸
   명확한 메시지로.
3. 레포 전체: argparse 도움말의 em dash가 Windows 한글 콘솔(cp949)에서
   `UnicodeEncodeError`로 CLI를 죽임 → em dash 전량 제거.
